# 墨水屏阅读器面试准备（零基础人话版）

> 这份文档假设：
>
> - 你没学过 FreeRTOS；
> - 你不知道什么是 Queue、Mutex、DMA；
> - 你没写过 C++ 项目；
> - 你只大概知道这是一个墨水屏阅读器。
>
> 先不要背高级词。先把下面的比喻看懂，再把每个比喻换成项目里的软件名字。

---

## 一、先记住这个项目是什么

### 最简单的一句话

这是一个用 **ESP32-S3** 做的电子墨水屏阅读器。

它像一台很小、只能显示黑白的平板电脑，里面有：

- 阅读器；
- 文件管理；
- 音乐；
- 相册；
- 时钟；
- 日历；
- 设置；
- 天气；
- 电子木鱼等。

### 面试开场先用最简单的话说

> 这是一个基于 ESP32-S3 的墨水屏阅读器。它可以看 TXT 电子书，也能管理文件、播放音乐、显示时钟和日历。屏幕是 2.7 英寸墨水屏，触摸屏用来翻页和点击。项目难点主要是墨水屏刷新慢、容易出现残影，还要同时处理触摸、文件和音频这些任务。

这句话先背熟。技术词后面再慢慢加。

## 二、把项目想成一家餐厅

这样理解最容易：

| 项目里的名字 | 餐厅里的角色 | 实际作用 |
|---|---|---|
| 用户 | 顾客 | 触摸屏幕、点击、看内容 |
| FT6336U | 门口的感应器 | 感知手指按在哪里 |
| UiBus | 前台收件箱 | 把各种消息排队送到 UI |
| UiLoop | 前台经理 | 处理消息，决定当前该做什么 |
| Router | 导航员 | 决定去哪个页面 |
| Composer | 后厨拼盘员 | 把当前页面和弹窗拼成一张完整画面 |
| Canvas | 画板 | 真正画线、画字、画图标 |
| Presenter | 放映员 | 把画好的内容送到屏幕 |
| GDEY027T91 | 显示牌 | 最终让你看到画面 |
| Presenter 任务 | 专门搬屏幕的人 | 不阻塞前台，慢慢刷新屏幕 |

一条最简单的链路：

```text
手指点屏幕
  -> 感应器收到
  -> 前台收到消息
  -> 经理决定怎么做
  -> 导航员决定去哪个页面
  -> 拼盘员准备好画面
  -> 放映员送到屏幕
```

面试官问“整体流程是什么”，你就先讲这条餐厅流程，再补充单词。

## 三、最基础的名词，全部翻译成人话

### 1. 硬件名词

| 名词 | 人话解释 | 在项目里是什么 |
|---|---|---|
| ESP32-S3 | 一块带 Wi-Fi 和蓝牙的小电脑芯片 | 项目的大脑 |
| 单片机 | 很小的计算机 | 控制屏幕、按键、传感器 |
| Flash | 断电也不会丢的仓库 | 保存程序、字体、图片 |
| SRAM | 工作台，速度快但地方小 | 放临时数据、任务栈 |
| PSRAM | 外接的大桌子 | 放更大的图片、缓冲区 |
| GPIO | 一根根可以输入输出的针脚 | 接屏幕、触摸、按键 |
| SPI | 一种高速串行通信方式 | 和屏幕、TF 卡通信 |
| I2C | 一种低速、只用两根线的通信方式 | 和触摸、音频芯片通信 |
| ADC | 把电压变成数字 | 读电池电压和拨码 |
| PWM | 快速开关来控制亮度或功率 | 控制背光 |
| 墨水屏 | 只能黑白、刷新慢、断电不丢画面的屏幕 | 项目主屏幕 |
| TF 卡 | 可插拔小存储卡 | 放书、音乐、照片 |
| 电池 ADC | 测量电池电压 | 估算剩余电量 |

### 2. 软件运行名词

| 名词 | 人话解释 | 容易误解的点 |
|---|---|---|
| 任务 Task | 系统里同时干活的人 | 不是函数，是独立运行的工作单元 |
| 线程 | 和任务类似 | 在 FreeRTOS 里通常叫 Task |
| 队列 Queue | 排队传纸条 | 一个任务写，另一个任务读 |
| 生产者 | 往队列放东西的人 | 例如触摸任务 |
| 消费者 | 从队列拿东西的人 | 例如 UI 任务 |
| 队列深度 | 队伍最多能站几个人 | 满了就会失败或等待 |
| 互斥锁 Mutex | 厕所门锁 | 一个人进去，其他人等 |
| 信号量 Semaphore | 车位数量、信号灯 | 用来通知和等待 |
| 事件组 Event Group | 一排指示灯 | 表示一个或多个状态完成了 |
| 中断 ISR | 门铃突然响 | 只做最紧急的事，不能慢慢处理 |
| ISR 安全 | 中断里专用的安全函数 | 不能随便用普通函数 |
| DMA | 专门搬货的搬运工 | CPU 不用亲自搬每一字节 |
| 栈 Stack | 每个人自己的便签纸 | 太小会溢出 |
| 堆 Heap | 项目共享的大仓库 | 借了要还，否则内存泄漏 |
| 内存泄漏 | 借了内存不还 | 用久了内存越来越少 |
| 死锁 | 两个人互相等对方让路 | 谁都不动，系统卡住 |
| 看门狗 | 监督员 | 程序太久不回应就重启 |

### 3. 项目架构名词

| 名词 | 人话解释 | 它解决什么问题 |
|---|---|---|
| UI | 用户界面 | 用户能看、能点的部分 |
| Router | 页面导航员 | 决定当前显示哪个页面 |
| Composer | 拼图员 | 把页面、状态栏、弹窗拼成一张图 |
| Presenter | 放映员 | 把拼好的图送到屏幕 |
| Canvas | 画板 | 画字、线、矩形、图标 |
| UiBus | UI 消息队列 | 让别的任务把消息交给 UI |
| UiLoop | UI 前台 | 不停地接收消息并处理 |
| Framebuffer | 一张屏幕大小的画布 | 保存准备显示的像素 |
| Back buffer | 草稿纸 | 先画在草稿纸，再送屏幕 |
| 双缓冲 | 一块画、一块显示 | 减少冲突和撕裂 |
| 环形缓冲 | 首尾相接的跑道 | 一直循环使用固定空间 |
| 驱动 | 翻译官 | 把软件命令翻译成硬件动作 |

### 4. 墨水屏刷新名词

| 名词 | 人话解释 | 面试时必须知道 |
|---|---|---|
| Full | 整张重画，最清楚但最慢 | 残影最少 |
| Fast | 快速重画 | 比 Full 快，残影更明显 |
| Partial | 局部补画 | 最快，但需要参照旧画面 |
| 局刷基线 | 参照的旧画面 | 基线不对，局刷就会出错 |
| 残影 | 上一张图的鬼影 | 墨水屏常见问题 |
| BUSY | 屏幕在说“我还在忙” | 不忙完不能发下一条命令 |
| 波形 | 屏幕翻转像素的方式 | 决定刷新速度和清晰度 |
| 8 像素对齐 | 每 8 个像素算一组 | SSD1680 的地址按字节组织 |
| 脏区 | 真正变化的区域 | 当前代码只做到整屏合成，Partial 波形 |

## 四、面试中最容易被问的 12 题，先给最简单答案

### Q1：这个项目是做什么的？

**人话版：**

> 它是一台用 ESP32-S3 做的墨水屏阅读器，可以看电子书，也能听音乐、看图片、管理文件、看时钟和日历。

**稍专业版：**

> 它是基于 ESP-IDF 和 FreeRTOS 的嵌入式图形系统，包含阅读器、文件管理、音频、时钟等应用，核心是墨水屏显示和 UI 架构。

### Q2：为什么要分成很多模块？

**人话版：**

> 因为一个人既当前台、又当后厨、还当放映员，很容易乱。分开后，每个人只做一件事，出了问题也容易查。

**稍专业版：**

> 通过 Router、Composer、Presenter、Canvas 分层，把路由、合成、刷新和绘制解耦，降低页面逻辑与硬件驱动的耦合。

### Q3：点击一下屏幕，程序做了什么？

**人话版：**

> 触摸芯片先告诉系统有手指按下，输入任务读取坐标，把点击事件送进 UiBus，UI 任务处理后再让画面和屏幕更新。

**稍专业版：**

> FT6336U 中断通知 -> InputRouter 任务读 I2C -> 手势识别 -> UiBus -> UiLoop -> Router -> Presenter -> Composer -> Canvas -> SPI -> BUSY 完成。

### Q4：墨水屏为什么不能像手机一样刷新？

**人话版：**

> 因为它靠墨水颗粒翻转，刷新慢，而且翻转不干净时会留下上一张图的影子。

**稍专业版：**

> 电子纸刷新波形耗时较长，Partial 刷新依赖已有基线，反复局刷会累积残影，需要定期 Full 重建基线。

### Q5：Full、Fast、Partial 是什么？

**人话版：**

> Full 是整张重画，最清楚但最慢；Fast 是快速重画；Partial 是只补一小块，最快但最容易有残影。

**稍专业版：**

> 三者对应 SSD1680 的不同刷新波形，分别在清晰度、速度、功耗和残影之间做权衡。

### Q6：为什么要有局刷基线？

**人话版：**

> 因为局部刷新要参考上一次显示的内容。旧画面不对，刷新后就会错位或留影子。

**稍专业版：**

> SSD1680 的 Partial 波形依赖 RAM 中的上一帧信息，因此必须维护 `base_ok_` 和有效基线。

### Q7：为什么刷新要等 BUSY？

**人话版：**

> 屏幕还在忙的时候，如果继续发命令，就像别人还在说话你硬塞下一句，画面可能乱掉。

**稍专业版：**

> BUSY 表示面板正在执行刷新波形，必须等待拉低或超时，避免命令序列与刷新时序冲突。

### Q8：UiBus 是什么？

**人话版：**

> 它是 UI 的收件箱。别的任务不能直接冲进 UI 改东西，只能把消息放进收件箱，让 UI 自己处理。

**稍专业版：**

> UiBus 是基于 FreeRTOS Queue 的多生产者单消费者事件总线，队列深度为 32。

### Q9：为什么不直接改 UI？

**人话版：**

> 因为多个任务同时改同一个页面，就像几个人同时改一份文档，很容易乱。

**稍专业版：**

> UI 状态只能在 UiLoop 中修改，其他任务通过 UiBus 投递事件，避免数据竞争。

### Q10：为什么要用 PSRAM？

**人话版：**

> 因为内部内存不够大，PSRAM 是外接的大桌子，可以放更大的缓冲和任务栈。

**稍专业版：**

> PSRAM 能缓解内存压力，但 DMA 缓冲、ISR 访问和实时路径仍有特殊限制。

### Q11：USB MSC 是什么？

**人话版：**

> 就是让设备在电脑上看起来像一个 U 盘。

**稍专业版：**

> USB MSC 把 `userdata` 分区暴露给主机，主机和应用不能同时写同一分区，需要先卸载应用侧再切换挂载点。

### Q12：OTA 是什么？

**人话版：**

> 就是不用插线，直接从网络下载新固件并升级。

**稍专业版：**

> OTA 通过双应用分区和 otadata 完成下载、校验、切换启动分区，失败时可以回滚。

## 五、面试官追问时，怎么把“人话”升级成“技术话”

你可以用这个公式：

```text
先说它解决什么问题
  -> 再说项目中用了什么方法
  -> 最后说为什么不用别的简单方法
```

例如：

> 我不用页面直接刷屏，是因为屏幕刷新慢，而且 SPI 和 BUSY 有时序要求。项目里用 Presenter 做异步队列，页面只提交刷新请求，Composer 负责合成，Presenter 负责上屏，这样触摸和网络不会阻塞在屏幕上。

## 六、必须会背的 8 条短答案

1. **项目一句话**：基于 ESP32-S3 的墨水屏阅读器，包含阅读、文件、音乐、时钟等应用。  
2. **架构一句话**：Router 管页面，Composer 管合成，Presenter 管上屏，Canvas 管绘制。  
3. **点击链路**：触摸中断 -> 输入任务 -> UiBus -> UiLoop -> Router -> Presenter -> Compositor -> 屏幕。  
4. **刷新模式**：Full 清晰慢，Fast 折中，Partial 快但依赖基线。  
5. **残影处理**：基线失效或残影明显时回退 Full。  
6. **并发处理**：UI 只在 UI 线程改，跨任务用 UiBus，共享资源用 Mutex。  
7. **存储处理**：TF 卡用 SDMMC + FAT32，USB 和 APP 切换挂载点前先卸载。  
8. **OTA 处理**：双分区、校验、切换启动分区、失败回滚。

## 七、哪些话绝对不能说

- 不能说：“Partial 就是只重绘变化区域。”  
  正确说法：“当前是整屏合成，使用 Partial 波形。”
- 不能说：“OTA 页面已经完全做好了。”  
  正确说法：“底层链路存在，完整页面还在完善。”
- 不能说：“所有代码都是我一个人从零写的。”  
  正确说法：“我负责其中一部分，其他部分使用现有框架或开源组件。”
- 不能说：“PSRAM 可以解决所有内存问题。”  
  正确说法：“PSRAM 缓解容量问题，但 DMA 和实时路径有额外限制。”

## 九、提前准备的三段口述

### 1 分钟口述

> 这是一个基于 ESP32-S3 的墨水屏阅读器。它用 2.7 英寸电子纸屏显示内容，支持触摸、Wi-Fi、BLE、音频和 TF 卡。软件上我采用分层的 UI 架构，把页面导航、画面合成、上屏和绘制分开；跨任务通过 UiBus 事件队列通信。项目的主要难点是墨水屏刷新残影、多任务并发和存储/USB MSC 的挂载冲突。

### 3 分钟口述

在上述内容后补充：

> 触摸芯片产生中断后，中断只通知系统，不直接读 I2C。输入任务读取坐标和识别手势，然后通过 UiBus 把事件送到 UI 线程。UI 线程决定页面是否跳转，Presenter 再在后台把 framebuffer 刷新到屏幕。墨水屏刷新分 Full、Fast、Partial 三种，局刷依赖基线，出现异常时回退 Full。

### 遇到不会的题

> 这个细节我没有在源码里做到那么深，我的理解是它和刷新时序/任务同步有关。如果继续排查，我会先看日志，再看对应驱动和任务，最后用最小实验验证。
