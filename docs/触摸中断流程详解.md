# 触摸中断流程详解（小白版）

这份文档只讲一件事：

> **手指碰到屏幕，到墨水屏刷新，中间到底经过了哪些函数，谁交给谁。**

每一步都回答同一个问题："这个函数跑完之后，下一步是谁？"

---

## 0. 先记住一张总图

```text
手指按下
   │
   ▼
[硬件] FT6336U 芯片把 INT 引脚拉低
   │
   ▼
[中断] int_isr_handler()            ← 中断服务函数，只做"敲门"
   │  xSemaphoreGiveFromISR() 给信号量发通知
   ▼
[任务] InputRouter::task_main()     ← 输入任务被唤醒
   │  wait_interrupt() 等到通知
   ▼
[任务] TouchGesture::poll()
   │  └─ Ft6336u::read()  通过 I2C 读坐标
   ▼
[任务] TouchGesture::process_sample()   ← 手势状态机判断
   │  产出 Tap / Swipe / LongPress
   ▼
[任务] InputRouter::drain_events()
   │  UiBus::post_input() 把事件塞进队列
   ▼
[UI  ] UiLoop::run()                ← UI 线程从队列取事件
   │
   ▼
[UI  ] UiLoop::handle_event() → UiLoop::dispatch_input()
   │  找到当前页面
   ▼
[UI  ] HomePage::on_input() 等页面处理点击
   │
   ▼
[UI  ] Router::navigate() 改页面 + 提交刷新请求
   │
   ▼
[后台] Presenter 合成画面 → 墨水屏驱动 → 真正刷新
```

记住两个关键点，后面就都好懂了：

1. **中断只负责"敲门"，不干活。**
2. **输入任务负责"识别手势"，但不改界面，只发消息。**

---

## 1. 第一步：手指按下，硬件触发中断

**谁在等？** FT6336U 芯片。

FT6336U 检测到手指，会把它的 INT 引脚拉低。这个引脚接到了 ESP32-S3 的 GPIO，
而且我们已经把这个 GPIO 配置成"触发中断"。

**代码在哪？** `main/bsp/driver/ft6336u/ft6336u.cc`

```cpp
void IRAM_ATTR int_isr_handler(void*)
{
    BaseType_t wake = pdFALSE;
    if (g_int_sem != nullptr)
        xSemaphoreGiveFromISR(g_int_sem, &wake);
    if (wake == pdTRUE)
        portYIELD_FROM_ISR();
}
```

**逐句人话：**

| 代码 | 意思 |
|---|---|
| `void IRAM_ATTR int_isr_handler` | 中断服务函数。`IRAM_ATTR` 表示代码放在内部 RAM，Flash 操作时也能跑 |
| `BaseType_t wake = pdFALSE;` | 准备一个变量，记录"这次有没有唤醒任务" |
| `xSemaphoreGiveFromISR(...)` | 给信号量发通知。这是中断里能用的安全版本 |
| `portYIELD_FROM_ISR()` | 如果唤醒了更高优先级任务，中断结束前立刻切过去 |

**这里故意什么都不多做**，只是"敲了一下门"。

**下一步是谁？** 输入任务 `InputRouter::task_main()`，因为它在等这个信号量。

### 为什么中断里不直接读坐标？

因为读坐标要走 I2C，一次可能几百微秒到几毫秒。在中断里等这么久会拖慢整个系统，
甚至让其它中断被推迟。所以：

> 中断只发通知，读坐标交给任务。

---

## 2. 第二步：输入任务被唤醒

**谁在等？** `input_router.cc` 里的采集任务。

```cpp
while (running_)
{
    if (!dev_->wait_interrupt(kIdlePollMs))   // 等中断，最多等 20ms
    {
        gesture_.poll();
        gesture_.tick();
        drain_events();
        process_release();
        continue;
    }

    // 等到了：手指在屏幕上，连续采集
    gesture_.poll();
    drain_events();
    ...
}
```

**`wait_interrupt()` 内部做什么？** 见 `ft6336u.cc`：

```cpp
bool Ft6336u::wait_interrupt(uint32_t timeout_ms)
{
    xSemaphoreTake(g_int_sem, 0);                                  // 先清旧标记
    return xSemaphoreTake(g_int_sem, pdMS_TO_TICKS(timeout_ms)) == pdTRUE;
}
```

就是 `take` 那个信号量。中断 `give`，任务 `take`，一配一。

**两种情况：**

- **等到中断** → 说明有触摸，进入"触摸阶段"，连续读、连续判断。
- **超时（20ms）** → 没有触摸。也要 `poll()` 一次 + `tick()`，
  因为可能刚好错过一次触发，或者需要推进长按计时。

**下一步是谁？** `TouchGesture::poll()`。

---

## 3. 第三步：读一次触摸

**函数：** `TouchGesture::poll()` / `Ft6336u::read()`

```cpp
bool TouchGesture::poll()
{
    if (touch_ == nullptr || pending_.type != GestureType::None)
        return pending_.type != GestureType::None;

    TouchSample sample = {};
    if (!touch_->read(sample))     // 走 I2C 读寄存器
        return false;
    return process_sample(sample); // 交给状态机
}
```

`Ft6336u::read()` 里做的事：

1. 读寄存器 `REG_TD_STATUS`，拿到"有几个触点"。
2. 每个触点解析出 x / y（各 12 bit）。
3. 做一次坐标校正（交换 / 翻转 / 裁剪）。

有个小细节：**它读了两次**。如果两次内容不一样，以第二次为准。
因为触摸芯片在更新瞬间读出来可能是旧数据，再读一次能大幅减少错误坐标。

**下一步是谁？** `TouchGesture::process_sample()`。

---

## 4. 第四步：状态机判断这是什么手势

**函数：** `TouchGesture::process_sample()`

这是整个手势识别的核心。它每次收到一个采样就走一遍，分三种情况：

### 情况 A：采样里没有触点（手指抬起了）

```
如果本来就没按        -> 忽略
如果驱动还说有手指    -> 可能只是读空了一帧，先不管
否则                 -> finish_contact() 结算
```

### 情况 B：本来没按，现在来了触点（刚按下）

```cpp
state_ = State::Pressed;
start_x_ = last_x_ = mapped_.x;   // 记录起点
start_y_ = last_y_ = mapped_.y;
press_start_ms_ = t;              // 记录按下时刻
stable_frames_ = 1;
```

### 情况 C：已经在按（手指还在）

```cpp
// 1. 更新"稳定帧数"：几乎没动就 +1，动了就清零
if (dfx <= 1 && dfy <= 1)
    stable_frames_++;
else
    stable_frames_ = 0;

// 2. 先判断长按（长按优先级高于移动）
if (try_long_press(t))
    return true;

// 3. 如果配置要求发移动事件，就发 Move
if (cfg_.emit_move && ...)
    push_event(GestureType::Move, ...);
```

**状态机只有三个状态：**

```text
Idle（没手指）
  │ 检测到触点
  ▼
Pressed（按着，还没判定）
  │ 按住够久 + 位置稳定
  ▼
LongPressSent（已发长按，等抬手）
  │ 抬手
  ▼
Idle
```

**抬手时** 由 `finish_contact()` 统一结算：

```text
1. 位移够大 + 时间够短  -> SwipeLeft/Right/Up/Down
2. 位移小 + 时间短      -> Tap
3. 都不是              -> 什么都不发
```

**下一步是谁？** 事件被写进 `pending_`，等 `drain_events()` 取走。

---

## 5. 第五步：把事件投进 UI 队列

**函数：** `InputRouter::drain_events()`

```cpp
void InputRouter::drain_events()
{
    while (gesture_.has_event())          // 只要还有事件
    {
        const Event ev = gesture_.take_event();   // 取出来
        (void)ui::UiBus::get_instance().post_input(ev);  // 投进队列
    }
}
```

`UiBus::post_input()` 做的事（`ui_bus.cc`）：

```cpp
UiEvent e = make_event(UiEventKind::Input);  // 标记类型
e.payload.input = ev;                        // 装数据
return post(e, 0);                           // 塞进 FreeRTOS 队列
```

**关键：这里是"复制"进队列，不是传指针。**
所以输入任务放完就可以走了，UI 线程之后照样能拿到完整数据。

**下一步是谁？** UI 线程 `UiLoop::run()`。

### 为什么输入任务不直接调用页面？

因为输入任务和 UI 线程是两个并行任务。如果输入任务直接去改
页面状态、改列表、改路由，就可能和 UI 线程同时改同一份数据，出难以复现的 bug。

> 输入任务只发消息，UI 线程负责处理消息。

---

## 6. 第六步：UI 线程取事件

**函数：** `UiLoop::run()`（`ui_loop.cc`）

```cpp
while (running_)
{
    if (!bus.recv(ev, portMAX_DELAY))   // 一直等，直到有事件
        continue;

    handle_event(ev);                   // 处理它

    while (running_ && bus.recv(ev, 0)) // 把积压的都处理掉
        handle_event(ev);
}
```

`portMAX_DELAY` 表示无限等待。没有事件时，UI 线程睡眠，不占 CPU。

**下一步是谁？** `handle_event()`。

---

## 7. 第七步：分流，找到当前页面

**函数：** `UiLoop::handle_event()`

```cpp
switch (ev.kind)
{
    case UiEventKind::Input:
        dispatch_input(ev.payload.input);  // 触摸事件
        break;
    // 还有 TickClock、TickBattery、WifiState ...
}
```

队列里不只触摸，还有时钟、电量、网络等事件，所以要先按类型分流。

**函数：** `UiLoop::dispatch_input()`

它按优先级决定"这次点击给谁处理"：

```text
1. 有确认弹窗   -> 给弹窗
2. 有键盘打开   -> 给键盘
3. 有控制中心   -> 给控制中心
4. 否则按当前页面：
     Lock     -> LockPage::on_input()
     Home     -> HomePage::on_input()
     AppGrid  -> AppGridPage::on_input()
     AppHost  -> AppHostPage::on_input()
```

**下一步是谁？** 某个页面的 `on_input()`。

---

## 8. 第八步：页面判断你点了哪里

以首页为例（`shell/home_page.cc`）：

```cpp
InputResult HomePage::on_input(const input::Event& ev)
{
    if (ev.type != EventType::Tap)
        return {};                       // 只处理点击

    if (reading_card_rect().contains(x, y))   // 点到"继续阅读"卡片
    {
        ReaderApp::request_resume_on_enter();
        r.navigate(router::page_app(AppId::Reader));  // 去阅读器
        return {true};
    }
    return {};
}
```

`rect().contains(x, y)` 就是在问："这个点在我这块区域里吗？"
和手机上判断有没有点中按钮是一个道理。

**下一步是谁？** `Router::navigate()`。

---

## 9. 第九步：改页面 + 提交刷新

**函数：** `Router::navigate()`

```text
1. 记录从哪页到哪页（Transition）
2. 查表决定用哪种刷新方式（全刷 / 快刷 / 局刷）
3. 真正修改页面栈
4. 把刷新请求交给 Presenter
```

**顺序很重要：先改页面，再提交刷新。**
因为后面的绘制是照着"新的页面栈"来画的，顺序反了会画出旧页面。

**下一步是谁？** `Presenter::submit()`。

---

## 10. 第十步：合成画面，异步上屏

**函数：** `Presenter::submit()`

```text
1. 调用 Composer::paint()，把当前页面画到"后备画布"
2. 把刷新请求放进 Presenter 自己的队列
3. 立刻返回
```

注意：**这里只是"提交"，屏幕还没刷。**

真正刷屏的是 `Presenter::task_main()` 这个后台任务：

```text
1. 从队列取请求
2. 丢掉过期请求，只保留最新的一个
3. 调用 execute() -> DisplayPort -> Gdey027t91::present()
4. 等墨水屏 BUSY 引脚变回空闲
```

**为什么要丢弃旧请求？** 因为墨水屏刷新慢。用户快速点十下，
前九张画面早就过期了，没必要一张张刷。

## 11. 整条链路的函数对照表

按"谁调用谁"的顺序，一行一个：

| 顺序 | 函数 | 跑在哪个线程/上下文 | 一句话作用 |
|---|---|---|---|
| 1 | `int_isr_handler()` | 中断 | 敲门：给信号量发通知 |
| 2 | `InputRouter::task_main()` | 输入任务 | 等中断，被唤醒 |
| 3 | `TouchGesture::poll()` | 输入任务 | 读一次触摸 |
| 4 | `Ft6336u::read()` | 输入任务 | I2C 读坐标 |
| 5 | `TouchGesture::process_sample()` | 输入任务 | 判断手势 |
| 6 | `InputRouter::drain_events()` | 输入任务 | 取事件 |
| 7 | `UiBus::post_input()` | 输入任务 | 投进 UI 队列 |
| 8 | `UiLoop::run()` | UI 线程 | 从队列取事件 |
| 9 | `UiLoop::handle_event()` | UI 线程 | 按类型分流 |
| 10 | `UiLoop::dispatch_input()` | UI 线程 | 找当前页面 |
| 11 | `HomePage::on_input()` | UI 线程 | 判断点了哪里 |
| 12 | `Router::navigate()` | UI 线程 | 改页面 + 提交刷新 |
| 13 | `Presenter::submit()` | UI 线程 | 合成画面 + 入队 |
| 14 | `Composer::paint()` | UI 线程 | 画到后备画布 |
| 15 | `Presenter::task_main()` | 上屏任务 | 取最新请求 |
| 16 | `Gdey027t91::present()` | 上屏任务 | 通过 SPI 操作墨水屏 |
| 17 | `Gdey027t91::wait_busy()` | 上屏任务 | 等刷新完成 |

## 12. 常见疑问

### Q1：为什么不用一个 `while(true)` 全做完？

因为墨水屏刷一次可能要几百毫秒到十几秒。
如果在主循环里等刷屏，触摸、音频、网络就全卡住了。
所以拆成多个任务，各自等待、各自让出 CPU。

### Q2：信号量是干什么的？

它是任务和中断之间的"门铃"。
中断按一下门铃（`give`），任务在门里等着（`take`）。
没有它，任务只能一直轮询，浪费 CPU。

### Q3：为什么事件要放进队列，而不直接调用？

因为跨任务直接调用会让两个任务同时碰同一份数据。
队列是线程安全的"传递通道"，复制一份数据过去，谁都不影响谁。

### Q4：触发中断函数后面是哪一步？

紧跟着就是：**输入任务从信号量醒来**。
中断函数 `int_isr_handler` 跑完，CPU 切回 `InputRouter::task_main`
（它正卡在 `wait_interrupt()` 里），从那里继续往下执行。

### Q5：想改触摸灵敏度去哪里改？

- 改"多短算点击""多快算滑动" → `touch_gesture.hpp` 里的 `GestureConfig`
- 改"某类页面用什么档位" → `gesture_tuner.cc` 里的 `make_config`
- 改"采集多快" → `input_router.hpp` 里的 `kIdlePollMs` / `kCoalesceMs`

## 13. 建议的阅读顺序

1. 先读本文的 0~4 节，把"中断 → 任务 → 手势"搞明白。
2. 再打开 `input_router.cc`，对照第 2、5 节读代码。
3. 然后打开 `touch_gesture.cc`，对照第 4 节读 `process_sample`。
4. 最后读 `ft6336u.cc` 的中断部分（有注释标出分段）。
5. 想继续看"点击之后怎么刷屏"，读 `docs/点击链路-逐行代码解释.md`。
