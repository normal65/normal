## 1. 先用一句话说清楚项目

这是一个基于 **ESP32-S3** 的墨水屏电子书阅读器。

硬件上用了一块 **2.7 英寸、264×176 的电子纸屏 GDEY027T91**，再加上触摸、音频、TF 卡、电池等模块。软件上用 **ESP-IDF + FreeRTOS** 开发，自己搭了一套 UI 管线，包含 `Router`、`Composer`、`Presenter`、`Canvas` 和 `UiBus`。

它不是一个只会显示文字的电子书，而是包含阅读器、文件管理、音乐、相册、画板、天气、时钟、日历、设置等多个应用的完整系统。

### 1.1 1 分钟面试开场

> 这是一个基于 ESP32-S3 的墨水屏阅读器项目，屏幕是 2.7 英寸的 GDEY027T91，系统里同时接了触摸、音频、TF 卡和电池采样。软件上我把界面拆成 Router、Composer、Presenter 和 Canvas 四层：Router 管页面跳转，Composer 负责把页面画到 framebuffer，Presenter 异步把画面刷新到墨水屏，Canvas 负责最终的一比特绘制。跨任务通信通过 UiBus 事件队列完成，避免后台任务直接修改 UI。
>
> 项目里最有代表性的难点有三个：第一是墨水屏的 Full、Fast、Partial 三种刷新和局刷基线；第二是 UI、刷新、存储、网络这些任务之间的并发；第三是 TF 卡热插拔和 USB MSC 挂载切换。

### 1.2 3 分钟版本

> 启动时会先初始化 NVS、存储、显示和音频这些基础服务，再启动 Presenter、UiBus、UiLoop 和输入任务。用户触摸屏幕后，FT6336U 的中断只负责通知，真正的 I2C 读点和手势判断在 InputRouter 任务里完成，然后通过 UiBus 把事件交给 UI 线程。
>
> UI 线程处理事件后，如果需要跳转页面，就调用 Router 修改页面栈；如果需要刷新，就向 Presenter 提交 FrameRequest。Presenter 在提交者任务里完成 Composer 绘制，再由自己的高优先级任务把后备 framebuffer 复制到屏幕驱动 framebuffer，最后通过 SPI 把画面写入 SSD1680 控制器，并等待 BUSY 结束。
>
> 墨水屏不能像普通 LCD 一样随便刷，所以项目区分 Full、Fast、Partial 三种波形。Partial 依赖已有基线，如果基线失效或残影明显，就必须用 Full 重建基线。

## 2. 面试前必须看懂的术语（先扫盲）

这一节放在最前面，是因为后面每一节都会用到这些词。
不用一次背完，先混个眼熟，读代码时再回来查。

### 2.1 硬件与通信

| 名词 | 人话解释 | 在本项目中的作用 |
|---|---|---|
| CPU | 执行程序的核心 | 运行 UI、驱动、网络和应用程序 |
| Flash | 断电后仍然保存数据的存储，类似硬盘 | 保存固件、字体、图片、配置 |
| SRAM | CPU 直接访问的内存，速度快，容量小 | 放栈、普通变量、DMA 缓冲 |
| PSRAM | 外扩内存，容量更大，速度比内部 SRAM 慢 | 放较大的缓冲、后台任务栈 |
| GPIO | 通用输入输出引脚 | 控制屏幕、触摸、按键、电源等 |
| SPI | 一种高速串行通信总线 | 屏幕、TF 卡、部分传感器 |
| I2C | 一种低速两线通信总线 | 触摸、音频控制器、运动传感器 |
| I2S | 音频专用串行总线 | 音频数据收发 |
| ADC | 模拟量转数字量 | 读取电池电压和拨码开关 |
| PWM | 通过占空比模拟不同输出强度 | 控制背光等 |
| BUSY | 屏忙信号 | 屏还在刷新时不能发下一条命令 |
| DMA | 直接内存访问 | 让数据搬运不占用大量 CPU |

| 术语 | 人话解释 | 项目中的意义 |
|---|---|---|
| RTOS | 实时操作系统 | FreeRTOS 提供任务、队列、信号量 |
| Task | 任务 | 可以理解为并发运行的线程 |
| Queue | 队列 | 任务之间传递消息 |
| Mutex | 互斥锁 | 防止两个任务同时改同一资源 |
| Semaphore | 信号量 | 用于通知、等待和同步 |
| Event Group | 事件组 | 用位表示一个或多个状态 |
| Producer | 生产者 | 往队列里发送数据的任务 |
| Consumer | 消费者 | 从队列里取数据的任务 |
| ISR | 中断服务函数 | 硬件事件发生时短暂执行 |
| ISR-safe | 中断安全 | 只能调用带 FromISR 的 FreeRTOS API |
| Framebuffer | 帧缓冲 | 保存一整屏像素或位图的内存 |
| Back buffer | 后备缓冲 | UI 先画到这里，再复制去刷新 |
| Double buffer | 双缓冲 | 一块画、一块刷，减少撕裂和冲突 |
| Ring buffer | 环形缓冲 | 固定大小、循环写入的数据队列 |
| NVS | 非易失存储 | ESP-IDF 保存配置的小型键值存储 |
| VFS | 虚拟文件系统 | 让不同文件系统使用统一路径 |
| Localhost preview | Host 模拟预览 | 在电脑上先看 UI 布局，不烧录 |

### 2.3 墨水屏专用

| 术语 | 人话解释 | 项目中的意义 |
|---|---|---|
| Full | 全刷波形 | 最清晰、最慢、最不容易残影 |
| Fast | 快刷波形 | 速度快，残影风险上升 |
| Partial | 局刷波形 | 最快，但必须有可用基线 |
| Baseline | 局刷基线 | 局部刷新用来对比的上一帧 |
| Ghosting | 残影 | 上一屏内容残留在下一屏 |
| Dirty region | 脏区域 | 本次真正发生变化的区域 |
| 波形 | 控制电子墨水颗粒运动的电压序列 | 决定刷新速度、清晰度和残影 |

### 2.4 存储与升级

| 术语 | 人话解释 | 项目中的意义 |
|---|---|---|
| FAT32 | 文件系统 | TF 卡和 userdata 的常见格式 |
| LittleFS | 嵌入式文件系统 | 保存字体、图标等资源 |
| SDMMC | TF 卡高速接口 | 4-bit 数据总线，比 SPI 快 |
| MSC | USB 大容量存储 | 把设备分区暴露给电脑 |
| OTA | 在线升级 | 通过网络下载并更新固件 |
| Rollback | 回滚 | 新固件启动失败时回到旧版本 |
| BLE | 低功耗蓝牙 | 连接手机或外设 |

## 3. 硬件：不然后面看不懂

### 3.1 ESP32-S3 是什么

ESP32-S3 是一颗带 Wi-Fi 和蓝牙的单片机。它可以理解成“一台很小的电脑”，
内部有 CPU、SRAM、Flash 接口、PSRAM 接口和大量外设控制器。

本项目用的是 **ESP32-S3-WROOM-1-N16R8**：

- `N16`：16MB Flash
- `R8`：8MB Octal PSRAM

### 3.2 GDEY027T91 是什么

GDEY027T91 是一块电子墨水屏模组，不是普通的彩色 LCD。

它的特点：

- 只有黑白两色，适合阅读文字；
- 断电后画面还在，不需要持续供电；
- 刷新速度慢，而且不同刷新模式有不同效果；
- 局部刷新依赖之前显示过的内容，也就是“局刷基线”。

屏幕内部使用的是 **SSD1680 兼容控制器**。ESP32-S3 不是直接“画像素到玻璃上”，而是通过 SPI 给 SSD1680 发命令和数据。

### 3.3 外设速查

| 模块 | 作用 | 接口 |
|---|---|---|
| FT6336U | 电容触摸控制器，读取手指坐标 | I2C + 中断 GPIO |
| ES8311 | 音频编解码器，负责播放声音 | I2S + I2C 控制 |
| QMI8658A | 加速度计和陀螺仪 | I2C |
| TF 卡 | 存书、音乐、照片、笔记等 | SDMMC 4-bit |
| 电池采样 | 读电池电压估算电量 | ADC |
| TPS61170 | 升压芯片，给墨水屏提供高压 | DC-DC |
| SY8088AAC | 降压芯片，把 5V 降到 3.3V | DC-DC |

## 4. 软件架构：把项目分成“楼层”

```text
应用层：阅读器、音乐、文件、设置、天气……
  ↓
UI 层：Router、Composer、Presenter、Canvas
  ↓
平台层：UiBus、UiLoop、输入、音频、存储、网络
  ↓
BSP 驱动层：GDEY027T91、FT6336U、ES8311、SDMMC……
  ↓
硬件：ESP32-S3、屏幕、触摸、TF 卡、电池
```

越往下越接近硬件，越往上越接近用户能看到的东西。

### 4.1 Router：页面路由器

Router 负责决定“当前显示哪个页面”。

它类似手机 App 里的页面导航。页面不是直接互相调用，而是告诉 Router：

- 我要前进到哪个页面；
- 我要返回上一页；
- 页面栈怎么变化；
- 这次变化应该用 Full、Fast 还是 Partial 刷新。

为什么要有 Router？如果每个页面都自己开关别的页面、自己决定刷新方式，
代码会越来越乱。Router 把这些决定集中起来。

### 4.2 Composer：画面合成器

Composer 负责“把当前应该显示的内容完整画出来”。

它会把当前页面、状态栏、Toast、弹窗、键盘按照层级合成到一块内存里。
这块内存叫 **framebuffer**。

### 4.3 Canvas：画布

Canvas 是绘图工具，提供画点、线、矩形、文字、图标等能力。

墨水屏是 1-bit 屏幕，每个像素只有黑或白两种状态，所以 Canvas 不需要处理复杂颜色。

### 4.4 Presenter：上屏调度器

Presenter 负责把已经合成好的画面刷新到屏幕。
它采用异步方式，因为屏幕刷新很慢：

1. UI 线程发出刷新请求；
2. Composer 把画面画到 `back_fb_`；
3. Presenter 的后台任务把 `back_fb_` 复制到屏幕驱动 framebuffer；
4. 屏幕驱动通过 SPI 把数据发给 SSD1680；
5. 等待 BUSY 结束。

### 4.5 UiBus：跨任务事件队列

UiBus 是本项目自己起的名字，不是行业标准专有名词。
它的本质是：**一个基于 FreeRTOS Queue 的 UI 事件队列。**

触摸、网络、时钟、电量、OTA、音乐等任务把事件投递到 UiBus，
UI 线程从 UiBus 取出事件处理。这样后台任务就不需要直接修改 UI 对象。

### 4.6 UiLoop：UI 主循环

```text
等待 UiBus 事件
  ↓
判断事件类型
  ↓
调用当前页面或覆盖层的处理函数
  ↓
必要时请求 Router 或 Presenter
```

## 5. 一条点击链路，必须能背

```text
手指触摸
  ↓
FT6336U 产生中断
  ↓
中断只释放信号量，不直接读 I2C
  ↓
InputRouter 任务读取坐标
  ↓
TouchGesture 判断点击 / 滑动 / 长按
  ↓
UiBus::post_input()
  ↓
UiLoop 从 UiBus 取出事件
  ↓
当前页面处理输入
  ↓
Router 修改页面栈
  ↓
Presenter 接收 FrameRequest
  ↓
Composer 绘制 framebuffer
  ↓
Presenter 后台任务执行上屏
  ↓
GDEY027T91 驱动通过 SPI 写 SSD1680
  ↓
等待 BUSY，刷新完成
```

面试官如果问“你为什么这么设计”，重点回答：

> 输入采集、UI 状态修改和硬件刷新拆开，是为了避免跨任务直接修改 UI，
> 也让慢速硬件刷新不阻塞触摸和页面逻辑。

更细的逐步讲解见 `docs/触摸中断流程详解.md`。

## 6. 高频问题与白话回答

### A. 项目介绍类

#### Q1：这个项目是做什么的？

这是一个基于 ESP32-S3 的墨水屏阅读器，除了阅读文字，还包含文件管理、音乐、相册、画板、天气、时钟、日历和设置等应用。我的重点是把显示、触摸、存储、网络和 UI 组织成一个可以扩展的系统。

#### Q2：你负责什么？

回答时只说你真的做过的部分。可以替换成下面任意一种表述：

- 我主要负责 UI 架构和显示链路；
- 我主要负责驱动适配和系统集成；
- 我主要负责应用框架、输入事件和调试工具；
- 我参与整体方案设计、模块联调和测试。

不要把开源组件也算成“我从零写的”。更稳妥的说法是“我在现有框架基础上完成适配、集成和扩展”。

#### Q3：为什么选墨水屏？

墨水屏适合阅读，断电后画面保留，功耗低；缺点是刷新慢、只有黑白、局刷容易残影。所以整个项目的设计重点之一就是怎么管理刷新。

### B. 架构类

#### Q4：为什么分 Router、Composer、Presenter、Canvas？

每一层只负责一件事：

- Router 管页面关系；
- Composer 管画面内容；
- Presenter 管上屏节奏；
- Canvas 管具体绘制。

这样改页面跳转不会影响屏幕时序，改刷新策略也不用重写每个页面。

#### Q5：为什么不让页面直接操作屏幕？

因为页面不应该知道 SPI、BUSY、波形和局刷基线。否则每个页面都要处理复杂硬件细节，容易产生冲突。页面只需要表达“我要显示什么”，Presenter 和驱动负责“怎么显示”。

#### Q6：UiBus 是标准组件吗？

不是。它是这个项目自己的命名，本质是 FreeRTOS Queue 封装出来的 UI 事件总线。

#### Q7：UiBus 为什么要存在？

因为触摸、网络、时钟、电量、OTA 可能由不同任务触发。如果它们直接操作 UI，容易出现数据竞争。UiBus 把跨任务消息统一交给 UI 线程处理。

#### Q8：UiBus 的队列满了怎么办？

普通事件如果发送失败就丢弃，避免后台任务卡死；关键事件比如阅读器索引完成，会选择阻塞等待，确保 UI 不会一直停在等待状态。

### C. 显示刷新类

#### Q9：Full、Fast、Partial 有什么区别？

- Full：全屏刷新，最清晰，耗时长，闪烁明显；
- Fast：速度更快，清晰度和残影之间折中；
- Partial：局部刷新，最快，但依赖局刷基线。

#### Q10：为什么要有局刷基线？

墨水屏局刷不是直接覆盖，而是参考上一帧计算哪些像素需要翻转。没有有效基线，局刷结果可能错误或者残影明显。

#### Q11：什么时候重建基线？

开机第一次刷新、页面大范围变化、模式恢复到稳定状态、局刷失败或残影明显时，通常用 Full 或 Fast 重建。

#### Q12：为什么局刷要 8 像素对齐？

因为 SSD1680 的横向地址按字节计算，一个字节对应 8 个像素。窗口起点和宽度必须对齐，否则可能写到错误位置。

#### Q13：Partial 是不是只画变化区域？

不是。当前项目的 Partial 主要是“整屏重新合成，但使用 Partial 波形”。如果要真正只画脏区，需要新增矩形传播、Composer 裁剪、Presenter 计划和驱动窗口联动。

#### Q14：为什么每次刷新都要等 BUSY？

BUSY 表示屏幕控制器还在执行上一次刷新。如果不等它结束就发新命令，可能造成刷新错位、花屏或者状态异常。

#### Q15：SPI 为什么要加锁？

屏幕初始化、刷新、休眠和测试可能来自不同调用路径。加锁可以保证一次 SPI 命令序列不会被另一条路径打断。

#### Q16：为什么选择 20MHz SPI？

这是速度和稳定性的折中。太高容易受布线、排线和信号质量影响，太低会导致刷新明显变慢。

### D. 多任务与并发

#### Q17：项目里有哪些任务？

至少可以讲：

- UI 任务：处理 UiBus 事件；
- Presenter 任务：执行上屏；
- 输入任务：读触摸和手势；
- 后台文件任务：扫描目录；
- 网络任务：Wi-Fi、NTP、OTA；
- Housekeeper：周期处理时钟、电量、热插拔等。

#### Q18：为什么输入任务不能直接改页面？

页面状态、ListView、Router 都可能被 UI 任务同时访问。跨任务直接改会破坏状态一致性。正确做法是把输入事件放入 UiBus。

#### Q19：Presenter 队列为什么只保留有限深度？

屏幕刷新慢。如果队列堆积大量旧帧，页面已经切走但屏幕还在刷旧内容。因此只保留少量请求，并且优先处理最新请求。

#### Q20：Mutex、Semaphore、Queue 有什么区别？

- Mutex 解决“谁占用共享资源”；
- Semaphore 解决“等待和通知”；
- Queue 解决“任务之间传数据”。

#### Q21：如果 Presenter 任务卡住怎么办？

先看最后一次执行到哪一层，再检查：

1. 是否卡在 BUSY 等待；
2. 是否发生 SPI 锁竞争；
3. 是否在文件或网络操作中阻塞；
4. 是否队列没有及时释放；
5. 是否任务栈或内存不足。

### E. 触摸与输入

#### Q22：中断里为什么不直接读 I2C？

I2C 读取可能等待、可能失败，不应该长时间占用中断。中断只记录“有触摸”，实际读取放到任务里做。

#### Q23：点击和滑动怎么区分？

通过采样点、移动距离、持续时间、滑动方向阈值和冷却时间判断。驱动只提供坐标，手势层负责把它翻译成事件。

#### Q24：触摸坐标不准怎么排查？

先确认屏幕旋转和镜像方向，再看触摸驱动的坐标映射，最后检查物理安装偏差。不要在多个层级重复翻转坐标。

### F. 存储、TF 卡和 USB

#### Q25：为什么用 SDMMC 而不是 SPI 接 TF 卡？

SDMMC 使用 4 位并行数据，速度明显高于 SPI，适合书籍、音乐、图片等大文件。

#### Q26：FAT32 适合这个项目吗？

适合。兼容 PC，方便用户插卡复制文件。但它没有日志，异常拔卡可能损坏文件系统，所以挂载、卸载和缓存刷新要谨慎。

#### Q27：热插拔怎么发现？

由 Housekeeper 周期性检查卡检测引脚。变化时挂载或卸载，并且做时间节流，避免频繁访问总线。

#### Q28：USB MSC 是什么？

USB MSC 是 Mass Storage Class，把设备分区模拟成 U 盘。电脑能看到 `userdata`，但同一时刻应用和电脑不能同时写它。

#### Q29：USB 和应用怎么避免挂载冲突？

切换挂载点之前先卸载应用侧，等待挂载迁移完成，再验证 VFS 是否可访问。整个过程需要互斥和超时保护。

### G. OTA、升级和分区

#### Q30：OTA 是什么？

OTA 是 Over-The-Air Update，通过网络下载固件并写入设备的另一个应用分区。

#### Q31：为什么要两个 OTA 分区？

因为不能覆盖正在运行的程序。系统把新固件写到另一个分区，校验通过后再切换启动分区，失败还可以回滚。

#### Q32：OTA 的完整流程是什么？

检查更新 → 下载固件 → 写入 OTA 目标分区 → 校验 MD5 或等价摘要 → 设置下次启动分区 → 重启 → 确认新固件可启动。

#### Q33：OTA 回调能不能直接改 UI？

不能。OTA 回调不在 UI 线程，正确做法是把进度和结果投递到 UiBus，再由 UiLoop 更新页面。

#### Q34：当前项目 OTA 完全完成了吗？

要分清“底层链路存在”和“产品页面完成”。当前代码里下载、分区、校验等底层能力存在，但完整更新页面仍然是待完善部分。回答时要如实说。

### H. 调试与工程能力

#### Q35：墨水屏不好调试，你怎么定位问题？

按链路分层排查：

1. 硬件供电和引脚；
2. SPI/I2C 是否正常；
3. 驱动命令和 BUSY；
4. framebuffer 是否有内容；
5. Composer 是否画对；
6. Presenter 是否提交；
7. Router 是否跳转；
8. 输入事件是否通过 UiBus 到达 UI。

#### Q36：怎么证明问题在 UI 而不是硬件？

如果 framebuffer 内容正确、驱动刷新也成功，但画面仍然不对，通常是合成或页面状态问题；如果 SPI 波形、BUSY 或驱动日志异常，则优先查硬件和驱动。

#### Q37：你怎么做回归测试？

至少覆盖：

- 触摸和滑动；
- 页面跳转；
- 读数翻页；
- 插入/拔出 TF 卡；
- USB 挂载切换；
- 电量变化；
- Wi-Fi 扫描；
- 音频播放；
- 重启后参数是否保留。

#### Q38：如果让你重做一次，你会改什么？

可以回答：

- 把真正的脏区刷新做成完整链路；
- 给 Presenter 增加更清晰的帧合并策略；
- 把 UI 预览和硬件自测扩展成自动化回归；
- 让 OTA 页面完整产品化；
- 把部分大模块拆得更细，降低耦合。

## 7. 项目难点：用 STAR 回答

### 难点 1：局刷残影

**S 情况**：局部刷新速度快，但文字边缘发灰或残留。  
**T 任务**：在不牺牲可用性的情况下保持画面清晰。  
**A 行动**：只在有有效基线时允许 Partial，异常时回退 Full/Fast，刷新失败后使基线失效。  
**R 结果**：局刷可用于快速交互，出现异常时可以恢复清晰画面。

### 难点 2：跨任务修改 UI

**S 情况**：触摸、网络和 UI 同时运行。  
**T 任务**：避免 UI 状态竞争和随机崩溃。  
**A 行动**：后台任务统一通过 UiBus 发事件，UI 状态只在 UiLoop 中修改。  
**R 结果**：模块之间解耦，问题更容易定位。

### 难点 3：屏幕刷新阻塞 UI

**S 情况**：墨水屏刷新耗时，直接调用会让界面无响应。  
**T 任务**：让刷新不阻塞输入和页面逻辑。  
**A 行动**：Presenter 使用独立任务和队列，UI 只提交 FrameRequest。  
**R 结果**：UI 处理与硬件刷新解耦。

### 难点 4：SPI 访问冲突

**S 情况**：刷新、休眠和初始化可能碰同一块屏幕。  
**T 任务**：保证命令序列完整。  
**A 行动**：驱动内部使用 bus mutex，刷新集中在 Presenter 任务。  
**R 结果**：避免命令交叉和状态错乱。

### 难点 5：TF 卡热插拔和 USB 切换

**S 情况**：应用和电脑都可能访问 userdata。  
**T 任务**：保证同一时间只有一个访问方。  
**A 行动**：先卸载、切挂载点、等待完成、再验证 VFS。  
**R 结果**：减少文件系统损坏和挂载失败。

### 难点 6：OTA 失败风险

**S 情况**：升级期间不能覆盖正在运行的固件。  
**T 任务**：让升级可校验、可回滚。  
**A 行动**：使用双 OTA 分区、写入目标分区、校验后切换启动区。  
**R 结果**：升级失败仍可回到旧系统。

## 8. 面试官最爱问：“你遇到过什么问题？”

这一节很重要。很多面试官不太关心你把架构背得多熟，
更关心**你是不是真的动过手、遇到问题会不会排查**。

回答这类问题的通用结构是四步：

```text
现象（看到了什么）
  ↓
定位（怎么一步步缩小范围）
  ↓
根因（最后发现是什么）
  ↓
解决 + 收获（怎么修的，以后怎么避免）
```

下面给你几个可以真实讲的故事模板。你只讲自己确实经历过的。

### 故事 1：板子焊完，电脑识别不到串口

**现象**：Type-C 插上后，电脑设备管理器里看不到新的 COM 口，
偶尔还能听到“叮咚、叮咚”的 USB 反复插拔声。

**排查过程**：

1. 先换一根确定能传数据的 Type-C 线，排除线的问题；
2. 用万用表量供电：5V 正常，但 3.3V 只有 0.56V；
3. 顺着电源链路查到 3.3V 降压芯片 SY8088AAC，发现 EN 脚电压不够；
4. 量 EN 脚对地阻抗，确认不是短路，而是没有稳定拉高；
5. 把 EN 正确拉到输入电压后，3.3V 恢复，芯片开始工作。

**根因**：降压芯片没有稳定使能，3.3V 上不去，主控根本没启动。

**收获**：嵌入式排障要先从**电源**开始，再查时钟、复位、通信。
供电不对，后面所有现象都不可信。

### 故事 2：屏幕亮了 2 秒又灭，USB 反复断开

**现象**：插电后屏幕能亮一下，然后黑掉，电脑同时出现 USB 断开又连接。

**排查过程**：

1. 先量 3.3V，确认电压是否稳定；
2. 观察“亮 2 秒”正好是屏幕开始刷新的时间点；
3. 推断是刷新瞬间电流变大，把电源拉低，触发主控复位；
4. 检查使能脚和电源余量，补强后恢复稳定。

**根因**：负载突变导致供电跌落，主控复位。

**收获**：间歇性重启优先怀疑**电源跌落 / 欠压复位**，
而不是先怀疑固件。用万用表长时间盯着电压看有没有跳动，很有用。

### 故事 3：触摸完全没反应

**现象**：屏幕能显示，但点哪里都没反应。

**排查过程**：

1. 先看日志里触摸芯片有没有初始化成功；
2. 用 I2C 扫描确认地址 `0x38` 能否读到；
3. 检查 INT 引脚有没有配置成输入、有没有打开中断；
4. 确认中断服务函数只给信号量发通知，实际读取在任务里；
5. 最后在输入任务里打印从 `poll()` 到 `post_input()` 的事件。

**根因**：可能是中断没开、I2C 没通，或者事件没进 UiBus。

**收获**：触摸问题要按 **硬件 → 驱动 → 手势 → 事件 → UI** 的顺序查，
每一层都能单独验证。

### 故事 4：局刷后文字发灰、残影明显

**现象**：快速翻页后，上一页的文字轮廓还留在屏幕上。

**排查过程**：

1. 确认当前用的是 Partial 波形；
2. 检查局刷基线是否有效；
3. 页面大范围变化时，强制切回 Full 重建基线；
4. 刷新失败时主动让基线失效，避免继续用错误基线。

**根因**：Partial 依赖基线，基线过期或内容变化太大就会残影。

**收获**：墨水屏的“快”是有代价的，刷新策略要和内容变化程度绑定。

### 故事 5：快速连点后页面卡住或显示旧内容

**现象**：连续点几次，屏幕最后显示的是中间某一帧，不是最新页面。

**排查过程**：

1. 检查 Presenter 队列是否堆积；
2. 确认后台任务会丢弃旧请求，只保留最新一帧；
3. 检查 UI 线程是否被 BUSY 等待阻塞；
4. 确认提交刷新和实际刷屏是异步的。

**根因**：慢速硬件 + 高频输入，如果不做帧合并就会排队刷过期画面。

**收获**：异步管线的关键不是“排队”，而是**丢弃过期任务、只做最新**。

### 故事 6：TF 卡拔插后文件系统异常

**现象**：热插拔 TF 卡后，有时挂载失败，或者文件列表不刷新。

**排查过程**：

1. 检查卡检测引脚和消抖；
2. 确认卸载时有没有等待正在进行的读写结束；
3. 挂载/卸载加互斥，避免 Housekeeper 和文件任务同时操作；
4. 失败后做重试，并给出可见的错误提示。

**根因**：文件系统和挂载点被多个任务同时访问。

**收获**：存储类问题要特别小心**并发和异常拔卡**，
不能假设用户会“安全弹出”。

### 故事 7：USB 挂载和 App 同时访问 userdata

**现象**：电脑通过 USB MSC 打开分区时，设备上的应用还在读写同一块区域。

**排查过程**：

1. 明确同一时刻只能有一个“所有者”；
2. 切换前先卸载应用侧 VFS；
3. 等待挂载迁移完成并验证可访问；
4. 全过程加互斥和超时，失败就回滚。

**根因**：两个访问方没有做好所有权切换。

**收获**：共享存储要有明确的**状态机**：应用独占 / 电脑独占 / 切换中。

### 故事 8：内存不够，任务栈溢出

**现象**：某个功能跑一会儿就重启，日志里出现栈溢出或分配失败。

**排查过程**：

1. 看任务栈水位，确认是不是栈给小了；
2. 看大缓冲是不是放在了内部 SRAM；
3. 把大块、非 DMA 的数据移到 PSRAM；
4. 检查队列深度和事件大小是否合理。

**根因**：嵌入式内存有限，栈和缓冲要按用途分配。

**收获**：不是所有内存都能随便用；PSRAM 也不等于“无限内存”，
而且不一定适合 DMA。

### 如果没有遇到过某个问题，怎么回答？

不要编。可以这样说：

> 这个问题我在项目里没有实际遇到，但我会按这个顺序排查：
> 先确认供电和硬件连接，再看驱动日志，然后用最小复现缩小范围，
> 最后对比正常和异常路径。如果方便，我可以现场看一下相关代码。

这样既诚实，又能体现你有排查方法。

### 排查问题的通用方法（很加分）

1. **先分层**：硬件 → 驱动 → 中间层 → UI，逐层确认。
2. **先最小化**：能不能用最小代码复现？能不能只保留一个模块？
3. **先对比**：正常和异常的两条路径差在哪里？
4. **先看日志和时间点**：问题发生前最后一条正常日志是什么？
5. **一次只改一个变量**：不要同时改三处，否则不知道是哪处生效。

## 13. 最后一页：面试官最可能追问的三句话

### 追问 1：“你这个项目的核心技术难点是什么？”

> 墨水屏刷新不是普通显示问题。它同时涉及波形选择、基线、BUSY 时序、
> SPI 并发和 UI 帧合成。我把刷新做成异步管线，并让异常时回退到 Full。

### 追问 2：“你怎么保证多任务不崩？”

> UI 状态只在 UI 线程改；跨任务用 UiBus；共享资源用 mutex；
> 慢任务放后台；关键结果通过事件回到 UI；队列有界并处理失败。

### 追问 3：“你最大的收获是什么？”

> 我理解了嵌入式项目不是“把每个函数写出来”就够了，
> 而是要同时考虑硬件时序、任务并发、内存限制、错误恢复和用户交互。
> 尤其是墨水屏项目，刷新策略本身就是系统架构的一部分。
>
> 另一个收获是排障方法：先电源、再通信、再驱动、最后 UI，
> 一次只改一个变量，这样问题不会越查越乱。
