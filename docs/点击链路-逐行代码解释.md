# 点击链路逐行代码解释（新手版）

> 这份文档只讲一件事：
>
> **手指点一下屏幕，到墨水屏真正刷新完成，代码到底一行一行做了什么。**
>
> 不要求你一次看懂全部。每段代码先看“这一步干什么”，再看代码下面的逐行解释。

---

## 一、先认识代码里的符号

### 1. `::` 双冒号

```cpp
ui::UiBus::get_instance()
```

意思是：

```text
ui 命名空间
  -> UiBus 类
    -> get_instance 函数
```

可以理解成地址：

```text
ui 家 -> UiBus 房间 -> get_instance 柜子
```

### 2. `.` 点号

```cpp
dev_->wait_interrupt(100)
```

`.` 表示“访问对象里面的成员”。

这里的 `dev_` 是一个触摸设备对象，`wait_interrupt` 是它里面的函数。

### 3. `->` 箭头

```cpp
dev_->wait_interrupt(100)
```

`dev_` 存的是一个对象的地址，所以用 `->`。

人话：

```text
dev_ 是一个路牌
-> 表示顺着路牌找到真正的对象
```

### 4. `{}` 大括号

```cpp
if (条件)
{
    做一些事情;
}
```

`{}` 里面就是这个条件成立时执行的代码。

### 5. `void`

```cpp
void foo()
```

`void` 表示这个函数**不返回结果**。

它只做事，不给你一个返回值。

### 6. `bool`

```cpp
bool ready()
```

`bool` 只有两种值：

```text
true  = 是
false = 否
```

### 7. `const`

```cpp
const int x = 10;
```

表示这个变量初始化后不能再改。

### 8. `auto`

```cpp
auto& r = Router::instance();
```

意思是“让编译器自己推断类型”。

你不用写出完整类型名字，但必须知道 `r` 是一个 `Router` 对象的引用。

### 9. `nullptr`

```cpp
if (g_int_sem == nullptr)
```

`nullptr` 表示“空的，没有指向任何对象”。

## 二、第一步：手指按下，FT6336U 中断

文件：

`main/bsp/driver/ft6336u/ft6336u.cc`

代码：

```cpp
void IRAM_ATTR int_isr_handler(void*)
{
    BaseType_t wake = pdFALSE;

    if (g_int_sem != nullptr)
        xSemaphoreGiveFromISR(g_int_sem, &wake);

    if (wake == pdTRUE)
        portYIELD_FROM_ISR();
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `void IRAM_ATTR int_isr_handler(void*)` | 定义一个中断处理函数，叫 `int_isr_handler` |
| `IRAM_ATTR` | 告诉 ESP32：这个函数很重要，放到快速内存里执行 |
| `void*` | 一个通用参数，这里没有用到具体内容 |
| `BaseType_t wake = pdFALSE;` | 建一个变量，记录“有没有唤醒更高优先级任务” |
| `if (g_int_sem != nullptr)` | 如果触摸中断信号量已经创建 |
| `xSemaphoreGiveFromISR(...)` | 在中断里给信号量发一个通知 |
| `&wake` | 把 `wake` 的地址传进去，函数可以修改它 |
| `if (wake == pdTRUE)` | 如果确实唤醒了任务 |
| `portYIELD_FROM_ISR();` | 中断结束时立刻切到那个任务 |

### 为什么不在这里读坐标？

因为中断要尽量快。

中断里只做一件事：

> 叮一下，告诉输入任务“有触摸了”。

真正读取 I2C 坐标放到任务里做。

## 三、第二步：输入任务读取触摸

文件：

`main/app/ebook/input/input_router.cc`

核心代码：

```cpp
void InputRouter::task_main()
{
    while (running_)
    {
        if (!dev_->wait_interrupt(kIdlePollMs))
        {
            gesture_.poll();
            gesture_.tick();
            drain_events();
            continue;
        }

        gesture_.poll();
        drain_events();
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `void InputRouter::task_main()` | 定义 `InputRouter` 类的任务主函数 |
| `while (running_)` | 只要输入任务还在运行，就不断循环 |
| `!dev_->wait_interrupt(...)` | 等待触摸中断；`!` 表示取反 |
| `kIdlePollMs` | 等待时间，避免一直死等 |
| `gesture_.poll()` | 读取一次触摸数据，推进手势判断 |
| `gesture_.tick()` | 推进时间状态，例如判断长按 |
| `drain_events()` | 把已经产生的手势事件全部取出来 |
| `continue` | 跳过本轮剩余代码，进入下一轮 |

### 这里的 `dev_` 是什么？

`dev_` 是 FT6336U 触摸设备对象。

`dev_->wait_interrupt()` 就是：

> 等触摸芯片发来“有手指”的通知。

### `gesture_` 是什么？

`gesture_` 是手势状态机。

它负责判断：

- 这是点击，还是滑动？
- 是短按，还是长按？
- 滑动是向左、向右、向上还是向下？

## 四、第三步：把事件放进 UiBus

文件：

`main/app/ebook/input/input_router.cc`

代码：

```cpp
void InputRouter::drain_events()
{
    while (gesture_.has_event())
    {
        const Event ev = gesture_.take_event();
        (void)ui::UiBus::get_instance().post_input(ev);
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `while (gesture_.has_event())` | 只要还有手势事件，就继续取 |
| `const Event ev = ...` | 取出一条输入事件，存到 `ev` |
| `gesture_.take_event()` | 从手势状态机里拿走一条事件 |
| `UiBus::get_instance()` | 取得全局唯一的 UiBus 对象 |
| `post_input(ev)` | 把输入事件投递到 UI 队列 |
| `(void)` | 表示“我知道这个函数有返回值，但这里不处理” |

### 为什么不能直接调用页面？

因为输入任务不是 UI 线程。

如果输入任务直接改页面、改列表、改 Router，就可能和 UI 线程同时修改同一个数据。

正确做法：

> 输入任务只负责发消息，UI 线程负责处理消息。

## 五、第四步：UiBus 把事件包装成 UI 消息

文件：

`main/app/ebook/ui/ui_bus.cc`

代码：

```cpp
bool UiBus::post_input(const input::Event& ev)
{
    UiEvent e = make_event(UiEventKind::Input);
    e.payload.input = ev;
    return post(e, 0);
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `bool` | 返回成功或失败 |
| `const input::Event& ev` | 收到一条输入事件，`&` 表示引用，不复制一份大对象 |
| `UiEvent e = make_event(...)` | 创建一条 UI 事件 |
| `UiEventKind::Input` | 标记这条 UI 事件的类型是“输入” |
| `e.payload.input = ev` | 把具体触摸数据放进事件内容里 |
| `return post(e, 0)` | 把 UI 事件放进队列 |

### `post()` 做什么？

```cpp
return xQueueSend(queue_, &ev, 0) == pdTRUE;
```

意思是：

> 把事件复制到 FreeRTOS 队列里。

`0` 表示不等待，队列满就立刻返回失败。

### 为什么是复制？

队列保存的是事件内容的一份副本。

所以生产者走后，消费者仍然能拿到完整的数据。

## 六、第五步：UiLoop 从队列取消息

文件：

`main/app/ebook/ui/ui_loop.cc`

代码：

```cpp
void UiLoop::run()
{
    auto& bus = UiBus::get_instance();
    UiEvent ev{};

    while (running_)
    {
        if (!bus.recv(ev, portMAX_DELAY))
            continue;

        handle_event(ev);

        while (running_ && bus.recv(ev, 0))
            handle_event(ev);
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `auto& bus = ...` | 取得 UiBus 的引用，不复制整个对象 |
| `UiEvent ev{}` | 创建一个空事件，等会儿用来接消息 |
| `while (running_)` | UI 线程持续工作 |
| `bus.recv(ev, portMAX_DELAY)` | 一直等，直到拿到一条事件 |
| `if (!...) continue;` | 如果没拿到，重新等 |
| `handle_event(ev)` | 处理这条事件 |
| `while (... bus.recv(ev, 0))` | 看看还有没有积压事件 |
| `handle_event(ev)` | 有就继续处理 |

### `portMAX_DELAY` 是什么？

表示“无限等待”。

没有事件时，UI 线程会睡眠，不浪费 CPU。

## 七、第六步：经理判断这是触摸事件

文件：

`main/app/ebook/ui/ui_loop.cc`

代码：

```cpp
void UiLoop::handle_event(const UiEvent& ev)
{
    switch (ev.kind)
    {
        case UiEventKind::Input:
            dispatch_input(ev.payload.input);
            break;

        default:
            break;
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `switch (ev.kind)` | 根据事件类型分流 |
| `case UiEventKind::Input:` | 如果这是输入事件 |
| `dispatch_input(...)` | 交给输入分派函数 |
| `ev.payload.input` | 从通用事件里取出输入数据 |
| `break` | 结束当前分支 |
| `default` | 其他类型暂时不在这里处理 |

### 为什么要用 `switch`？

UiBus 里不只有触摸事件，还可能有：

- 时钟事件；
- 电量事件；
- Wi-Fi 状态；
- OTA 进度；
- 系统提示。

所以要根据 `kind` 分开处理。

## 九、第八步：首页判断你点了哪里

文件：

`main/app/ebook/shell/home_page.cc`

代码：

```cpp
InputResult HomePage::on_input(const input::Event& ev)
{
    auto& r = router::Router::instance();

    if (ev.type != EventType::Tap)
        return {};

    const int16_t x = static_cast<int16_t>(ev.x);
    const int16_t y = static_cast<int16_t>(ev.y);

    if (reading_card_rect().contains(x, y))
    {
        apps::reader::ReaderApp::request_resume_on_enter();
        (void)r.navigate(router::page_app(AppId::Reader));
        return {true};
    }

    return {};
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `auto& r = Router::instance()` | 取得导航员对象 |
| `ev.type != EventType::Tap` | 如果不是点击，就不处理 |
| `ev.x` / `ev.y` | 从输入事件里取出触摸坐标 |
| `static_cast<int16_t>` | 把坐标转成有符号整数 |
| `reading_card_rect().contains(x, y)` | 判断点击是否落在最近阅读卡片里 |
| `request_resume_on_enter()` | 告诉阅读器：下次进入时恢复阅读 |
| `r.navigate(...)` | 请导航员去阅读器页面 |
| `return {true}` | 表示这个点击已经被首页处理了 |

### 这个 `rect()` 是什么？

`rect` 就是矩形区域。

`contains(x, y)` 就是问：

> 这个点在不在这块区域里面？

这和手机上判断“有没有点中按钮”是一样的。

## 十、第九步：Router 修改页面并提交刷新

文件：

`main/app/ebook/router/router.cc`

代码：

```cpp
core::Status Router::navigate(PageId to,
                              NavAction action,
                              const RefreshIntent* override_intent)
{
    const PageId from = stack_.current();
    Transition t{from, to, action};

    RefreshIntent intent =
        override_intent != nullptr
            ? *override_intent
            : RefreshEdges::resolve(t);

    const core::Status route_st = apply_route_change(to, action);
    if (route_st != core::Status::Ok)
        return route_st;

    return submit_transition(t, intent);
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `PageId to` | 目标页面 |
| `NavAction action` | 前进、返回、替换还是重绘 |
| `override_intent` | 是否强制指定刷新方式 |
| `stack_.current()` | 当前页面 |
| `Transition t{from, to, action}` | 描述这次页面变化 |
| `RefreshEdges::resolve(t)` | 查表决定用哪种刷新波形 |
| `apply_route_change(...)` | 真正修改页面栈 |
| `submit_transition(...)` | 把刷新请求提交给 Presenter |

### 为什么先改路由，再提交刷新？

因为 Composer 之后要根据新的页面栈来画画面。

如果先刷新再改页面，画出来的还是旧页面。

## 十一、第十步：Presenter 合成画面并排队

文件：

`main/app/ebook/presenter/presenter.cc`

代码：

```cpp
core::Status Presenter::submit(const FrameRequest& req)
{
    if (!started_)
        return core::Status::NotInit;

    (void)wait_idle(kSubmitTmoMs);

    if (xSemaphoreTake(fb_mutex_, pdMS_TO_TICKS(kSubmitTmoMs)) != pdTRUE)
        return core::Status::Timeout;

    composer::Composer::instance().paint(back_fb_);

    if (xQueueSend(queue_, &req, 0) != pdTRUE)
    {
        xSemaphoreGive(fb_mutex_);
        return core::Status::Timeout;
    }

    xEventGroupClearBits(state_evt_, kBitIdle);
    xSemaphoreGive(fb_mutex_);

    return core::Status::Ok;
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `if (!started_)` | Presenter 还没启动就不能接收 |
| `wait_idle(...)` | 等上一次上屏结束，避免堆积 |
| `xSemaphoreTake(fb_mutex_, ...)` | 拿到 framebuffer 的锁 |
| `Composer::paint(back_fb_)` | 把页面画到后备缓冲 |
| `xQueueSend(queue_, &req, 0)` | 把上屏请求放进 Presenter 队列 |
| `xSemaphoreGive(fb_mutex_)` | 释放 framebuffer 锁 |
| `xEventGroupClearBits(...)` | 标记当前不再空闲 |
| `return core::Status::Ok` | 表示请求已经成功入队 |

### 这里为什么有两个“队列”？

项目里有两层队列：

1. **UiBus 队列**：给 UI 线程送输入、网络、时间等事件。
2. **Presenter 队列**：专门送“上屏请求”。

可以理解成：

```text
UiBus     = 公司总收件箱
Presenter = 放映部门自己的任务单
```

## 十二、第十一步：Composer 把页面画出来

文件：

`main/app/ebook/composer/composer.cc`

代码：

```cpp
void Composer::paint(uint8_t* back_fb)
{
    gfx::Canvas canvas{back_fb, core::Rect::full(), dark};
    canvas.clear(gfx::Ink::White);

    const auto& stack = router::Router::instance().stack();

    switch (stack.shell_top())

        case router::ShellPage::Home:
            shell::HomePage::instance().paint(canvas);

            break;

        case router::ShellPage::AppHost:
            shell::AppHostPage::instance().paint(canvas);
            break;
    }

```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `back_fb` | 指向后备画布 |
| `gfx::Canvas canvas{...}` | 用这块内存创建画布 |
| `Rect::full()` | 画布范围是整个屏幕 |
| `canvas.clear(...)` | 先把画布清成白色 |
| `Router::stack()` | 获取当前页面栈 |
| `switch (stack.shell_top())` | 看当前最上层页面是什么 |
| `HomePage::paint(canvas)` | 调用首页画自己 |
| `StatusBar::paint(canvas)` | 再画状态栏 |
| `AppHostPage::paint(canvas)` | 如果在 App 页面，就画 App 页面 |

### 为什么叫“合成”？

因为最终画面不是只画一个页面，而是按顺序叠加：

```text
先画当前页面
再画状态栏
再画弹窗
再画 Toast
再画确认框
```

叠加完成后，才是一张完整画面。

## 十三、第十二步：Presenter 后台任务真正上屏

文件：

`main/app/ebook/presenter/presenter.cc`

代码：

```cpp
void Presenter::task_main()
{
    FrameRequest req{};

    while (running_)
    {
        if (xQueueReceive(queue_, &req, portMAX_DELAY) != pdTRUE)
            continue;

        FrameRequest extra{};
        while (xQueueReceive(queue_, &extra, 0) == pdTRUE)
            req = extra;

        xSemaphoreTake(fb_mutex_, portMAX_DELAY);
        (void)execute(req);
        xSemaphoreGive(fb_mutex_);
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `FrameRequest req{}` | 准备一个刷新请求变量 |
| `xQueueReceive(...)` | 从 Presenter 队列取任务 |
| `portMAX_DELAY` | 没任务时一直睡，不占 CPU |
| `FrameRequest extra{}` | 再准备一个临时变量 |
| `while (... recv(..., 0))` | 把队列里剩下的旧请求都取出来 |
| `req = extra` | 只保留最后一个请求 |
| `xSemaphoreTake(fb_mutex_)` | 锁住 framebuffer |
| `execute(req)` | 执行上屏 |
| `xSemaphoreGive(fb_mutex_)` | 解锁 |

### 为什么只保留最后一个请求？

因为墨水屏刷新慢。

如果用户快速点了十次，前九张画面可能已经过期了。

所以 Presenter 只保留最新的一张，减少无效刷新。

## 十四、第十三步：真正刷新屏幕

文件：

`main/app/ebook/presenter/presenter.cc`

代码：

```cpp
core::Status Presenter::execute(const FrameRequest& req)
{
    auto& port = display::DisplayPort::instance();
    const bool can_partial =
        (port.session() == display::SessionState::PartialReady);

    PresentPlan plan = make_plan(req.intent, can_partial);

    copy_fb();
    core::Status st = run_plan(plan);

    return st;
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `DisplayPort::instance()` | 取得屏幕适配层 |
| `port.session()` | 查询屏幕当前可不可以局刷 |
| `PartialReady` | 表示局刷基线已经准备好 |
| `make_plan(...)` | 把刷新意图变成具体步骤 |
| `copy_fb()` | 把后备画布复制到屏幕驱动画布 |
| `run_plan(plan)` | 按照步骤执行刷新 |

### `PresentPlan` 是什么？

它是一张刷新步骤表。

比如：

```text
第一步：建立基准
第二步：全屏刷新
```

或者：

```text
第一步：局部刷新
```

## 十五、第十四步：驱动真正操作墨水屏

文件：

`main/bsp/driver/gdey027t91/gdey027t91.cc`

代码：

```cpp
bool Gdey027t91::present(Present kind)
{
    if (!ensure_hw())
        return false;

    BusGuard lock(*this);
    if (!lock.ok())
        return false;

    switch (kind)
    {
        case Present::Full:
            return present_full();

        case Present::Fast:
            return present_fast();

        case Present::Partial:
            return false;
    }
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `ensure_hw()` | 检查硬件是否正常 |
| `BusGuard lock(*this)` | 试着锁住屏幕总线 |
| `lock.ok()` | 锁成功才继续 |
| `switch (kind)` | 根据刷新模式选择函数 |
| `present_full()` | 全屏刷新 |
| `present_fast()` | 快速刷新 |
| `Present::Partial` | 没有窗口参数时不能直接局刷 |

### `BusGuard` 是什么？

它像一把门锁。

进入屏幕操作前先锁门，操作完成后自动解锁，避免两个任务同时给屏幕发命令。

## 十六、第十五步：等待墨水屏忙完

文件：

`main/bsp/driver/gdey027t91/gdey027t91.cc`

代码：

```cpp
bool Gdey027t91::wait_busy(uint32_t timeout_ms) const
{
    uint32_t elapsed = 0;

    while (is_busy())
    {
        if (elapsed >= timeout_ms)
            return false;

        TaskMgr::delay_ms(1);
        ++elapsed;
    }

    return true;
}
```

### 逐行解释

| 代码 | 意思 |
|---|---|
| `is_busy()` | 读 BUSY 引脚 |
| `while (is_busy())` | 只要还在忙，就继续等 |
| `elapsed >= timeout_ms` | 超过最大等待时间 |
| `return false` | 报告超时失败 |
| `TaskMgr::delay_ms(1)` | 睡 1ms，把 CPU 让给别人 |
| `++elapsed` | 累计已经等了多少毫秒 |
| `return true` | BUSY 结束，刷新完成 |

### 为什么要超时？

如果排线松了、屏幕坏了或者供电异常，BUSY 可能一直不结束。

没有超时，Presenter 任务会永远卡住。

有超时，系统至少能报错并恢复。

## 十八、你现在应该先记住什么

先不用背下面这些函数内部怎么写。

你只要先记住：

1. **中断只通知，不读坐标。**
2. **输入任务识别手势，但不直接改 UI。**
3. **UiBus 是 UI 收件箱。**
4. **UiLoop 永远在 UI 线程处理消息。**
5. **Router 决定去哪个页面。**
6. **Presenter 异步负责上屏。**
7. **Composer 负责把画面拼出来。**
8. **Canvas 负责真正画像素。**
9. **GDEY027T91 驱动负责 SPI 和 BUSY。**
10. **提交成功不代表屏幕已经刷完。**

先把这 10 条背下来，再回来读每一段代码。
